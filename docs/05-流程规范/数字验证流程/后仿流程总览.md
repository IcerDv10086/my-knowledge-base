# 后仿流程总览

结合实际项目经验，本文聚焦后仿工作的标准执行流程，目标是让流程可复用、问题可定位、结论可验收。

## 1. 后仿目标与适用场景

后仿本质是使用带有时序信息的网表进行动态仿真。相比前仿与静态时序分析（STA），后仿更接近硅片真实时序行为，能够暴露动态时序问题。

后仿通常安排在前仿功能稳定后、芯片 Tape-out 前：

- 大规模芯片：后仿耗时长，通常按风险优先级筛选关键用例。
- 小规模芯片：在排期允许时建议全量覆盖，若资源受限则同样按优先级执行。

## 2. 输入物清单

- 门级网表（Netlist）
- 时序文件（SDF）
- 标准单元库与存储器模型
- 测试平台（Testbench）
- 约束与激励文件
- 版本信息（网表/SDF/库模型对应版本）

## 3. 标准执行链路

### 3.1 准备阶段

- 明确仿真工具与版本（本文以 VCS.2106 为例）。
- 对齐目录结构、文件组织与版本管理规范，确保团队内一致。
- 建立输入物一致性检查：网表、SDF、库模型、测试平台版本必须一一对应。

### 3.2 环境适配

与 RTL 仿真相比，后仿主要差异在于加载网表与时序：

- 在 filelist 中引入网表与标准库单元文件（通常为 .v）。
- 使用 VCS 的 SDF 仿真选项，或在环境中通过系统任务 `$sdf_annotate` 进行 SDF 加载。
- 检查设计侧的行为模型（如 analog/behavior model）是否已适配为可后仿形式，并补齐延迟信息。

关键检查项：

- 实例路径是否与 SDF 标注路径一致。
- 时序单位与精度设置是否匹配。
- 多角（PVT）或多模式场景是否选择了正确的 SDF。

!!! note
    1. 一般优先覆盖 SS_MAX、FF_MIN 两个高风险工艺角；如项目签核有额外要求，再补充 TT 或其他 PVT 角。
    2. 若采用系统任务加载 SDF，建议通过宏统一管理 `$sdf_annotate()` 的文件路径和实例路径，避免不同用例重复改动。
    3. 若采用 VCS 命令行加载 SDF，建议沉淀为统一模板，并根据工艺角正确选择 `min/typ/max` 类型：
        ```shell
        # two-step flow: 在编译/展开阶段登记 SDF
        vcs -sdf max:tb_top.u_dut:./sdf/chip_ss_max.sdf [compile_options]
        ./simv [run_options]

        # 也可在运行阶段指定
        ./simv -sdf min:tb_top.u_dut:./sdf/chip_ff_min.sdf [run_options]
        ```

### 3.3 编译阶段检查

编译阶段主要关注编译日志健康度，确保无阻断级 error，warning 信息在可接受范围内。

一些 VCS 编译/展开阶段常用选项（按需启用）：

```shell
vcs -diag=sdf:verbose -negdelay
```

需要额外关注的细节：

- timescale 设置：建议所有顶层及关键子模块统一声明为 `1ps/1ps`，避免因精度不足导致时序误判。
- IO、behave_model 等库的宏定义：如需屏蔽功能或切换为 timing 模型，务必与设计侧宏定义保持一致。
- 悬置端口、数据位宽不匹配 warning：如 warning 数量异常增多，需重点排查端口未连接或自动连线失效。
- 构建产物可用性：确认生成可执行文件（如 `simv`）及对应运行脚本，避免进入回归后才暴露环境问题。

常见检查项：

- 编译日志健康度检查：确认无阻断错误，warning 需要评估。

### 3.4 仿真阶段反标确认

SDF 反标实际在仿真运行阶段完成，核心目标是确认：时序延时是否完整、正确地加载到网表中。

检查依据：仿真日志中的 SDF 标注统计信息，以及诊断选项输出的反标明细（不同工具版本输出文件名可能不同）。

关键检查项：

- 反标覆盖率：确认关键实例与关键时序路径已反标，未反标项需有归因和处理动作。
- 反标一致性：确认 `min/typ/max` 选择与当前回归工艺角一致，避免角与 SDF 文件错配。
- 反标异常项：重点排查实例路径不匹配、网表命名差异、SDF 语法或模型映射问题。
- 时序检查状态：确认未被全局关闭（如误用 `+notimingcheck` 或 `+nospecify`）。

!!! note
    行业通用实践：将未反标项分为“可接受 waive”和“必须修复”两类。可以依据项目，进行脚本化做反标结果筛选。

### 3.5 Sanity 仿真

先执行小规模 sanity，用于快速验证环境可用性与关键检查策略。

常见实践：

- 对复位初期或特定一级触发器合理关闭时序检查（如 noSpecify）。
- 建议由验证与设计协同执行该阶段检查，减少定位偏差。
- 通过 UCLI/TCL 指令在运行时按场景动态开关 tcheck。
- 先关注“是否可稳定跑通”，再逐步收紧时序检查范围。

### 3.6 回归仿真与 Timing Violation 闭环

对关键用例进行后仿回归，重点关注 timing violation。

回归策略：

- 小芯片策略：在资源允许时优先全量跑完，再对失败用例做时序归因；这是最稳妥、也最省沟通成本的方式。
- 大芯片策略：按风险分层筛选回归，不追求数量最多，优先覆盖最容易触发时序风险的场景。

推荐分层：

- P0 必跑：上电复位、主时钟切换、跨时钟域数据同步、关键中断/异常路径、关键配置寄存器读写。
- P1 高优先：高吞吐数据通路、边界条件（最小间隔/突发/背靠背）、低功耗切换、关键外设主流程。
- P2 补充：长尾场景、低频功能、历史稳定且风险较低路径。

筛选维度：

- 时钟与复位复杂度：多时钟、时钟门控、异步复位释放路径。
- CDC/RDC 风险：跨域握手、异步输入同步链、复位跨域传播。
- 路径深度与负载：组合逻辑深路径、扇出大路径、关键仲裁路径。
- 工作模式覆盖：功能模式、配置模式、异常恢复模式。
- 历史问题热点：曾出现 timing violation 或 silicon bug 的模块优先。

时序违例定位思路（实战）：

1. 使用同一 case、同一 seed 进行前仿复现，建立可比对基线。
2. 对违例对应 cell 逐级向上定位到模块顶层，确认触发条件与传播路径。
3. 对比前后仿关键波形，判断是否影响功能；结论不明确时与设计联合评审。

常见违例原因：

1. 芯片外部异步 shutdown 复位建模不完善，导致边界时序扰动。
2. 多周期计算模块在计算窗口内输入被改写，导致路径时序检查触发。

## 4. 输出物与通过标准

建议输出物：

- 不同 SDF 反标结果报告（覆盖率、未反标项分类与解释）
- 关键波形与检查点说明
- 问题清单（现象、根因、责任方、状态）
- 回归结果汇总（通过率、风险项、残留问题）

建议通过标准：

- 反标结果可解释且关键路径覆盖满足项目要求
- 关键场景后仿回归通过
- 所有 timing violation 均有明确归因与处理结论
- 残留风险已评审并得到项目级别确认
