# CP Debug 记录

## 问题背景

某项目验证过程中，使用 EDA 工具仿真复现 CP 测试阶段发现的问题：

**问题现象**：芯片在使用标定 pattern 时预期结果不收敛。

**预期行为**：标定计算完成后，相关寄存器结果应保持一致。

## 测试环境模拟

### 影响变量

1. **初始化配置状态差异**：芯片具有OTP流程，而不同芯片在**前序测试阶段**写入的配置内容（flash_init）具有随机性，导致初始状态参数不统一。

2. **测试 Pattern 特性**：CP 测试使用的 pattern 为预定义**配置序列**和检查，其时序为确定的。

3. **加载时序不确定性**：算法控制模块运行时存在执行延迟不确定性，无法保证精确时间同步。

### 测试用例设计

| 用例 | 目标 | 配置 | 预期 |
| :--- | :--- | :--- | :--- |
| case1 | 同一芯片 CP 流程,及初始化配置内容相同，加载时序随机 | 不同伺服模式 | - |
| case2 | 不同芯片 CP 流程，及初始化配置内容随机，加载时序随机 | 不同伺服模式 | - |

测试思路（核心为控制变量法）：

1. 定义一个随机种子范围，`FIX_SEEDS_RANGE`，设置了100个
2. 对与case1，测试 pattern 的配置随机和初始化配置随机，均从`FIX_SEEDS_RANGE`中抽取随机数`FIX_SEED`。加载时序和数模接口的随机由EDA工具随机数控制，打印检查结果和`FIX_SEED`。
3. 对于case2，仅测试 pattern 的配置随机从`FIX_SEEDS_RANGE`中抽取随机数。其余均有EDA工具随机数控制，打印检查结果和`FIX_SEED`。
4. 超大量回归，回归1000次以上，保证每个`FIX_SEED`执行至少10次。
5. 通过脚本分析检查结果和`FIX_SEED`。相同的`FIX_SEED`，检查结果应一致。

> 将测试 pattern的配置向量随机化的目的是模拟实际配置的向量空间，避免仅考虑单一配置序列，遗漏一些未知问题。但由于实际配置间向量空间较大，个人认为这里选取100个随机数可以覆盖大部分配置空间。

## 根因分析

验证仿真未考虑初始化配置状态差异和加载时序不确定性，导致实际结果与预期不一致：

**温度补偿配置不一致:**

配置文件中温度开关状态不统一，结合测试序列启动时的随机延迟，导致温度补偿功能生效状态不确定，引起标定输入数据不一致。

**伺服开关配置和工作模式的特殊关系:**

- 工作模式1：进入配置序列后，需额外1-2计算周期完成模块初始化，建议间隔200us。
- 工作模式2：进入配置序列前，若某功能打开，需等待其完成初始化后再进入。

**寄存器配置时序竞争：**

寄存器配置阶段，初始需关闭计算开关，完成后需等待1个计算周期再配置后续内容，否则会引发时序问题。
