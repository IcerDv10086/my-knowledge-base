# lsTurbo 集群使用指南

## 1. 核心原理

lsTurbo 是一个基于 **OpenShift/Kubernetes** 构建的云原生 EDA 计算平台，其核心设计思想是 **“容器化”** 与 **“环境一致性”**。

*   **容器化计算**：每个 EDA 任务（仿真、调试、综合等）都运行在一个独立的、轻量级的 **容器** 中。容器内封装了完整的工具链和依赖环境，确保了“一次构建，处处运行”。
*   **统一资源调度**：由 Kubernetes 负责容器的生命周期管理、资源调度（CPU/内存）和在集群节点间的分发。
*   **高性能共享存储**：采用全闪存 NFS 架构，为所有容器和门户节点提供高速、一致的共享文件系统访问。用户的 Home 目录、EDA 工具库、项目数据均通过 NFS 挂载。
*   **交互式与批处理融合**：支持创建交互式容器（用于实时调试）和非交互式容器（用于批量任务），灵活适配不同工作流。

## 2. 常用命令及场景

以下命令均在集群门户节点（如 `gw0`, `gw1`）上执行。

| 命令 | 用途 | 典型场景 |
| :--- | :--- | :--- |
| **状态与生命周期管理** | | |
| `turbo ls` | 列出当前用户的所有容器及其状态（运行中/已停止）。 | 查看有哪些任务在运行，获取图形容器的连接链接。 |
| `turbo rm <podname>` | 停止并删除指定的容器，释放其占用的资源。 | 单个任务完成或出错后，清理容器。 |
| `turbo rm --all` | 停止并删除当前用户的所有容器。 | 每日下班前或定期清理，避免资源闲置。 |
| `turbo whereami` | 显示当前终端是位于门户节点还是某个容器内，并显示容器信息。 | 不确定当前环境时进行确认。 |
| **交互式容器（用于开发/调试）** | | |
| `turbo shell zsh` | 创建一个**命令行交互式容器**并立即进入。 | 需要运行命令行 EDA 工具（如 `vcs`, `dc`）进行编译或调试。 |
| `turbo shell --gui zsh` | 创建一个**图形界面交互式容器**，返回连接 URL，并进入命令行。 | 需要启动带图形界面的工具（如 `verdi`, `vivado`）进行调试或分析。 |
| `turbo attach <podname>` | 在**已运行**的交互式容器上打开一个新的控制台连接。 | 图形界面断开后重新连接，或需要多个终端会话操作同一个容器。 |
| **大内存交互式容器** | | |
| `turbo shell --gui --xlarge zsh` | 创建拥有 2核/32GB 资源的图形容器。 | 运行内存消耗较大的仿真或分析任务。 |
| `turbo shell --gui --2xlarge zsh` | 创建拥有 4核/64GB 资源的图形容器。 | 运行大规模 SoC 仿真。 |
| `turbo shell --gui --4xlarge zsh` | 创建拥有 8核/128GB 资源的图形容器。 | 运行极端内存需求的任务。 |
| **非交互式容器（用于批量任务）** | | |
| `turbo exec <command>` | 创建一个非交互式容器，执行指定命令后自动退出。 | 在 CI/CD 流水线中运行单个编译或测试命令。 |
| `turbo exec --no-stdout <command>` | 同上，但不实时输出日志。 | 提交后台任务，稍后查看结果。 |
| `turbo log <podname>` | 查看由 `exec` 创建的非交互式容器的输出日志。 | 检查已提交的批处理任务的结果。 |
| **初始化与认证** | | |
| `turbo init` | 初始化用户目录和配置（仅需一次）。 | 新用户首次使用集群。 |
| `turbo login` | 进行每日集群认证（需要每天执行）。 | 每天第一次使用集群前。 |
| `turbo addkeytab` | 为容器添加存储访问凭证（密码修改或系统升级后需执行）。 | 首次使用或遇到存储挂载错误时。 |

**关键工作流提示**：
*   **从容器退出**：在容器内输入 `quit` 会终止容器；输入 `detach` 会断开连接但容器在后台继续运行。
*   **图形连接断开**：只要未在容器内 `exit`，使用 `turbo ls` 找到容器名，再用 `turbo attach` 即可重新连接命令行，用返回的 URL 可重连图形界面。
*   **环境一致性**：容器内已预置 EDA 工具环境，**无需**手动 `source` 诸如 `common_settings.sh` 等配置脚本。
*   **图形界面容器**：通过创建图形界面容器，您会同时获得一个完整的图形桌面环境（通过XPRA访问）​ 和一个功能齐全的命令行终端（zsh）。

## 3. lsTurbo 与 LSF 核心对比

lsTurbo 和 LSF 都是用于管理大规模 EDA 计算任务的集群系统，但设计哲学和实现方式有根本不同。

| 维度 | **lsTurbo 集群** | **LSF (Load Sharing Facility)** |
| :--- | :--- | :--- |
| **核心架构** | **云原生，容器化**。任务以**容器**为单位，由 Kubernetes 调度。 | **传统 HPC，进程化**。任务以**作业**为单位，由 LSF 调度器管理进程。 |
| **用户交互模式** | **交互式优先**。用户通过 `turbo shell` 直接“进入”一个完整的、隔离的 EDA 环境进行操作，类似远程工作站。 | **提交-等待式**。用户编写作业脚本，通过 `bsub` 提交到队列，异步等待结果。交互性弱。 |
| **资源视角** | 用户申请的是一个个**完整应用环境**（容器），资源以容器为单位分配和限制。 | 用户申请的是抽象的**计算资源**（如 CPU 核数、内存量），由系统决定在哪个物理节点运行。 |
| **环境管理** | **强一致性**。工具、库依赖全部封装在容器镜像中，彻底杜绝环境差异问题。 | **依赖系统配置**。需要管理员统一维护所有计算节点上的软件和环境，维护成本高。 |
| **核心技术栈** | Kubernetes/OpenShift, Docker, NFS, XPRA (远程图形)。 | LSF 调度器，SSH， NFS。 |
| **适用场景** | **设计、调试、交互分析**。适合需要频繁操作图形界面、快速迭代、环境隔离要求高的前端设计阶段。 | **大规模批量仿真、回归测试**。适合吞吐量要求极高、任务可高度脚本化的后端验证阶段。 |
| **入门与调试** | **更友好**。直接获得一个可交互的完整环境，问题定位更直观。 | **有门槛**。需要熟悉作业脚本编写和日志查看，调试环境问题可能更复杂。 |

**总结**：
lsTurbo 代表了从传统 HPC 向云原生、开发者体验优先的 EDA 基础设施的演进。它通过容器技术提供了**环境绝对一致、开箱即用、支持交互**的计算平台，特别适合现代敏捷芯片设计流程。而 LSF 则在管理超大规模、高吞吐量的批处理作业队列方面依然具有其优势。两者并非简单替代，而是针对不同工作负载的优化解决方案。许多大型公司会采用混合模式，在交互开发环节使用 lsTurbo 类平台，在批量验证环节使用 LSF。
