# DV_checklist

DV checklist，一般又称**验证检查清单**，用于芯片验证各阶段工作完成后，逐项检查、核验交付输出物是否满足验证流程规范和设计标准，是芯片顺利投产流片的核心前置准入条件。

行业内项目阶段划分粒度各有差异，**最低标配划分为前仿真、后仿真两大核心阶段**；多数企业会在芯片正式投片前统一完成全量复盘评审。部分研发团队结合项目节奏，进一步将前仿真拆分为多个细分节点，分阶段开展清单核对与评审确认，层层收紧验证质量标准。

以下是结合常见 checklist 和本人的工作经验，总结出的验证检查清单，一般按阶段分批执行，项目周期紧张时至少项目介绍前一次性完成所有内容的checklist，但个人建议最少分成验证准备、前后仿验证两个阶段。

## 1. 验证准备阶段

核心目标：对齐设计意图，敲定验证目标，环境基本落地，确保验证工作基础。

- 设计文档反串讲
    - **反压过冲**问题是否在文档中明确说明
    - **异常处理机制**是否在文档中明确说明
    - 有无特定的**配置流程**和**配置间约束**，如果有需要在文档中说明

- DUT RTL 确认
    - 所有设计参数（parameter）是否符合预期并被测试覆盖
    - 所有的宏定义列表是否正确
    - 所有**固定电平（tie-off）的值**是否符合预期

- 接口确认
    - 与上游IP负责人/系统工程师确认本IP输入引脚在**POR、复位、低功耗**、正常工作状态下的**输出状态及值**
    - 与下游IP负责人/系统工程师确认本IP输出引脚在**POR、复位、低功耗**、正常工作状态下的**输入需求值**
    - 子系统与全芯片验证需增加对**上下游接口时序的串讲评审**

- testplan 评审
    - 复位特性
        - 多复位源场景，复位先后顺序随机，多复位源配置之间的**极限条件**
        - 同一条测试用例多次带业务流，进行复位
    - 时钟特性
        - 单时钟源时钟的属性随机，一般验证环境支持时钟属性随机化
        - 多时钟源情形覆盖频率最大、最小组合
    - 寄存器特性
        - 正常数据通路测试用例，需增加动态改配无关寄存器
        - 支持**动态改配**类型寄存器
    - 中断特性
        - 确保**中断能被正常触发和清除，在同一个测试用例中经历多次中断响应**
        - 确保**中断的屏蔽（mask）和禁用（disable）功能被测试到**
    - 时序特性
        - 全芯片验证是否梳理了与**多周期路径**相关的功能特性
        - 全芯片是否梳理**跨时钟域（CDC）**相关特性
    - 总线特性
        - 遍历所有总线传输类型与传输尺寸（最小、最大、随机）的组合
        - 事务内和事务间的**随机延迟**，延迟值需经过DE审查
        - 覆盖**背靠背（back2back）传输**、**大延迟传输场景**，以及**两者交替出现的场景**，覆盖多次反压
        - 在**输入数据无效（non-valid）时，输入随机值或给X**
        - 如果有**多个通道，确保有所有通道同时传输的测试用例**
    - 数模混合特性
        - 连通信测试：数包模架构下，数字顶层的输入信号需要保证不插入buffer到内部模拟顶层
    - 压力测试
        - 一个压力测试用例让所有数据通路都动起来，并随机各种配置
        - 所有的FIFO覆盖上溢和下溢场景
        - 所有的计数器覆盖上溢和下溢场景
        - 异步时钟相位及频率需要随机审查
        - 低功耗模式切换的压力测试
- 验证环境 & tbench 评审
    - 时钟源的抖动、占空比、频偏是否设置
    - 自研 Agent 时序联合设计侧联审，并 signoff
    - ref_model 和 scoreboard 检查方式是否符合预期

## 2. 前仿验证阶段

核心目标：所有功能收敛，随机场景稳定，前仿回归 pass。

- `XPROP` 未知态传播仿真，全用例稳定 PASS
- 寄存器随机初始化 INIT_REG 场景全覆盖，全用例稳定 PASS
- `EOT`检查增加，全用例稳定 PASS
    - DUT 状态机、接口、中断等是否在仿真结束时恢复预期状态
    - 验证环境各组件（**ref_model\scoreboard** 必须开启） check_phase 所有事物是否都已处理

- 核心业务流、异常流、边界流关键波形复盘确认

- testplan 迭代评审
    - 新增用例逐条 review
    - 测试用例逻辑与设计逐一对标，无场景遗漏、无激励偏差
    - 测试计划上的所有测试用例是否已经被实现，必须全部实现
    - 库中的所有代码是否都已写入测试计划，未写入需要说明原因，如支持DE测试、CP环境复现等，并做出明确区分
    - 所有功能测试用例，是否都已加入回归测试列表，未加入需要说明原因

- 验证环境 & tbench 迭代评审：
    - 约束与配置流
    - 功能覆盖组详细说明
    - 所有`force`尽量clear,一定要force的信号需要说明理由，并注意时序影响
    - 所有的`todo`,`FIXME`等注释，必须清除，不能保留任何未处理的事项
    - 编译 + 仿真日志全量审查，清除 ERROR、CRITICAL WARNING，普通 WARNING 分类归档说明
    - ref_model和scoreboard 全量被设计review，确保符合预期

- 覆盖率闭环评审
    - IP代码覆盖率达到100%
    - Top-level的IO信号toggle覆盖率需达到指定百分比（waive后）
    - 所有的waive文件已经过DE（设计工程师）审查，signoff包括层次化配置文件
    - 未覆盖场景统一提交 WAIVER，经架构 / 设计评审审批

- 需求与问题管理(一般使用JIRA等缺陷管理工具)
    - 历史 BUG 复盘 + 遗留问题分级评审（P0/P1/P2 风险定级）
    - 过去两个星期内新发现的Bug数量为0
    - JIRA（或缺陷管理工具）中所有Bug的状态已被全部关闭
    - 因场景构造问题，之前可以互相提验证需求jira

- 前仿持续回归：连续两周全量用例 100% PASS，无偶现失败
- 回归测试通过率为100%（未达100%时，所有失败案例需解释原因）

## 3. 后仿验证

核心目标：贴合真实芯片时序，验证时序 + 功能双重合规。

- SDF 时序反标正式报告输出
    - 时序反标覆盖率统计、未成功反标节点分类、原因说明与风险评估

- 跨时钟域、全局 / 局部复位逻辑专项复盘
    - 复位序列、异步复位释放、特殊复位场景波形逐一审阅
    - **芯片 PAD 对外接口**、**内部高频跨时钟节点**统一挂载 glitch_detect_sva 毛刺检测断言

- 全 PVT 工艺角回归稳定通过（TT/SS/FF、高低温、高低电压全覆盖）
- 在启用SDC约束的情况下运行仿真，并添加断言检查多周期路径
- 运行具有随机时钟周期/相位抖动的仿真
- RTL仿真中启用时序指定块时，应仔细检查，仅启用必要模块的时序指定
- BUG 与遗留问题 review

## 4. 实践细节

- 子系统与全芯片之间关键场景的验证环境分工需经审查，并提交**流程单跟踪**
- 所有阶段输出文档、日志、波形、报告统一归档，版本可追溯
- 阶段准入 / 准出标准严格执行，上一阶段未签核严禁进入下一阶段
- **偶现随机性失败问题优先复现、定位根因，禁止直接放行**
- DV 与前端设计、后端物理、DFT 团队同步进度，提前对齐风险，紧急情况下前仿初步稳定后通过后端可开始go forward
- 设计往往会遗漏一些配置约束，在验证发现后一定要让设计团队及时修复
