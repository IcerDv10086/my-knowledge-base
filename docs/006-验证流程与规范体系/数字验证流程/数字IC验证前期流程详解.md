# 从Spec到环境：数字IC验证前期流程详解

## 1. 文档定位与适用范围

本文聚焦数字IC验证前期最关键的三个动作：阅读Spec、制定Testplan、搭建验证环境。目标是给出一套可执行、可复用、可追溯的方法，帮助在项目早期把需求理解和验证落地风险降到最低。

适用范围：

- 模块级验证。
- 子系统级验证。
- 第三方IP集成验证。

不在本文覆盖范围：

- SoC层级全芯片验证。
- PSS、Formal等专项进阶技术。

## 2. 输入资料与准备工作

在正式开始前，先确认输入资料完整性，避免“边做边补文档”导致反复返工。

必备输入：

- 芯片或模块规格说明书（Spec）。
- 架构文档与接口定义文档。
- 模块设计详设文档与时序说明。
- 寄存器说明（如CSR map、字段语义、访问副作用）。
- IP/VIP文档
    - 协议规格
    - 寄存器与配置说明
    - 集成guideline
    - 约束与随机化、覆盖组
    - 参考示例的验证环境

!!! note
    项目输入不强制要求文档物理分离，但应至少覆盖**规格、架构接口、设计详设**三类信息；三类内容可在一份文档中合并呈现。
    若设计详设暂未齐备，验证可在已冻结的规格与接口约束基础上启动；但需同步维护“假设清单”和“待澄清问题清单”，并通过反串讲持续闭环，避免后期集中返工。

推荐输入：

- 历史Bug清单与复盘资料。
- 旧版本验证计划或可复用环境组件说明。

启动前检查清单：

1. 文档版本是否一致并冻结到本轮里程碑。
2. 关键术语与状态定义是否统一。
3. 接口时序、复位行为、错误处理路径是否有明确描述。
4. 未决问题是否形成跟踪清单并明确责任人。

## 3. Spec阅读方法论

### 3.1 阅读目标与输出物

Spec阅读不是“看完文档”，而是把自然语言需求转成可验证对象。建议输出三类结果：

- **功能点清单**：配置路径、正常路径与异常路径。
- **疑问清单**：歧义描述、缺失定义、边界冲突。
- **风险清单**：高复杂度状态机、跨时钟域处理、多复位交叉。

### 3.2 分层阅读策略

建议采用“**先全局后局部、先主流程后异常**”的方式，逐步建立对模块的完整理解：

1. 先理解模块功能本身
    - 搞清楚模块“做什么”、输入输出是什么、最基础的功能规格含义是什么。
    - 先建立功能全局认知，不急着钻实现细节。
2. 再按接口和控制面做粗分层
    - 接口先按功能划分分类理解。
    - 对时钟、复位、总线接口先建立“它负责连接前后级/配置/控制”的粗粒度认识即可。
    - 如果是公司自研总线或常规配置IP，先把它当作配置与控制通路处理，不必一开始展开到协议实现深处。
3. 最后结合架构图和需求点梳理数据通路
    - 根据架构图，把和需求相关的模块链路找出来。
    - 明确每个需求会流经哪些模块、经过哪些中间状态或通路。
    - 这样后面做testplan时，测试点和覆盖点会更容易落地。

通过以上分层阅读策略，可逐步建立正确的**心智模型**，确保对模块的理解全面且深入，避免早期被局部描述带偏。

### 3.3 需求拆解与标注规范

把需求按类型拆解并做统一标注：

- 功能类需求：行为正确性。
- 配置类需求：寄存器字段与模式组合。
- 时序类需求：握手时序、时钟域相关约束。(设计容易忽略)
- 异常类需求：错误码、恢复机制、保护行为。

每条需求建议同时标注可控点与可观测点，为后续用例设计与监测器实现做准备。

!!! note
    **需求点**本身不是功能点，是目标和问题的描述。**功能特性**是需求的具体实现，是验证的目标。一般一个功能特性会有多个**功能点**。**测试点**是对功能点的细化和拆解。但实际使用中，大家经常混用，所以这些名词的使用需要根据上下文判断。
    需求： “芯片需要联网。”（宏观目标）
    功能特性： “支持TCP/IP协议栈。”（一个核心特性）
    功能点： “实现TCP三次握手连接建立。”（一个具体的、可验证的 Feature）
    测试点1：正常三次握手连接建立。
    测试点2：SYN包超时重传。
    测试点3：重复SYN包处理。

## 4. 需求澄清与反串讲机制

在制定Testplan前，建议执行一次反串讲：由验证侧反向讲解对设计的理解，设计侧确认或纠偏。

反串讲最小输出物：

- 对齐后的功能点列表。
- 边界与异常场景列表。
- 待确认问题闭环记录（含责任人与截止日期）。

反串讲的价值在于把偏差前移暴露，减少后续测试写完才发现方向偏差的高成本返工。

## 5. Testplan制定方法

### 5.1 Testplan核心结构

一份可执行的Testplan至少应包含：

- 验证范围与不验证范围（In/Out Scope）。
- 验证策略（白盒、黑盒、灰盒的适用边界）。
- 测试点。

### 5.2 需求到测试点映射

核心原则是可追溯：需求必须能映射到测试点，再映射到具体用例与覆盖项。

建议采用如下链路：

需求ID -> 测试点ID -> 用例ID -> 覆盖率项 -> 回归结果

### 5.3 Testplan规划思路框架

制定Testplan时，建议从以下多个维度系统性地覆盖验证空间，确保验证的完整性和高效性：

- **基础验证维度**
    - 时序类验证
        - 接口协议时序（APB/AHB/AXI等）
        - 跨时钟域（CDC）验证
        - 建立/保持时间检查：数模混合芯片需要额外注意
        - 时钟域切换
    - 复位验证（RST）
        - 冷复位/热复位/软件复位
        - 复位时序与恢复时间
        - 多复位域交叉复位
        - 复位状态寄存器初始化
    - 寄存器与存储器扫描
        - 寄存器读写访问（正常/异常访问权限）
        - 寄存器位域读写验证
        - 访问副作用验证（写1清、读清等）
        - SRAM/ROM/存储阵列的读写完整性
        - 存储器边界地址访问

- **场景与功能维度**
    - 场景类验证
        - 冒烟场景：最小功能流程，快速验证环境基本连通性
        - 典型应用场景：覆盖用户最常用的工作模式
        - 组合场景：多模块/多功能协同工作场景
    - 功能类验证
        - 按功能点树形结构逐层拆解至最小可验证单元
        - 每个功能点对应多个测试点（正常/边界/异常）
        - 数据通路验证：输入→处理→输出全链路
        - 控制通路验证：状态机跳转、模式切换

- **性能与异常维度**
    - 性能类验证
        - 带宽/吞吐量验证
        - 延迟/响应时间验证
        - 资源利用率（如FIFO深度、缓存命中率）
        - 针对指纹芯片等特定场景：最快报点率、识别速度等
    - 异常类验证
        - 异常输入场景（非法指令、越界访问、错误数据包）
        - 错误处理与恢复机制
        - 超时处理
        - 容错与降级模式

- **补充验证维度（可选）**
    - 配置组合类验证
        - 寄存器配置组合爆炸问题处理
        - 关键配置组合正交验证
        - 多模式切换验证
    - 功耗类验证（如适用）
        - 低功耗模式验证
        - 时钟门控验证
        - 电源域切换
    - 可测性设计（DFT）类验证
        - 扫描链测试
        - JTAG/BIST验证
        - MBIST测试

- **规划实践建议**

- 采用迭代方式：先搭骨架（基础验证+核心场景），再逐步填充细节
- 每个测试点都应关联到需求ID，保证可追溯性
- 优先级不应只按功**能"重要程度"**，还应结合**失效风险**和**定位成本**。建议按P0/P1/P2分层：
    - P0：高风险核心路径，优先纳入sanity
    - P1：主功能与高频场景
    - P2：低频边界或扩展场景
- 测试点粒度适中：既不过粗导致覆盖不全，也不过细导致维护困难
- 与设计团队密切沟通，避免验证范围偏差

## 6. 验证环境搭建流程

### 6.1 架构设计原则

对于模块级和子系统层级，推荐使用UVM搭建可扩展环境，并使用随机激励、动态检查、覆盖率采集三个核心功能，实现以覆盖率为驱动的验证。

### 6.2 Agent

激励通过Agent模拟实现。一个Agent包含trans、sqr、driver、monitor和cfg，负责模拟一组相关功能接口的信号交互。

个人经验：按实际交互的模块进行拆分，每个Agent负责模拟一个前后级模块的激励与响应行为。中断信号建议设计一个专用Interface采集中断信号，并直接传送到sequence中使用。

sequence层层封装示例：

```systemverilog
// Layer 1: 基础数据单元
class uart_transfer extends uvm_sequence_item;
    rand bit [7:0] data;
    rand bit       parity;
    bit            error;
    `uvm_object_utils_begin(uart_transfer)
        `uvm_field_int(data, UVM_ALL_ON)
        `uvm_field_int(parity, UVM_ALL_ON)
    `uvm_object_utils_end
endclass

// Layer 2: 基础sequence
class uart_base_seq extends uvm_sequence #(uart_transfer);
    `uvm_object_utils(uart_base_seq)
    virtual task body();
        `uvm_info("SEQ", "uart_base_seq started", UVM_HIGH)
        req = uart_transfer::type_id::create("req");
        start_item(req);
        assert(req.randomize());
        finish_item(req);
    endtask
endclass

// Layer 3: 协议级sequence（组合多个基础transfer）
class uart_frame_seq extends uart_base_seq;
    rand int num_bytes;
    `uvm_object_utils(uart_frame_seq)

    virtual task body();
        `uvm_info("SEQ", $sformatf("uart_frame_seq started, %0d bytes", num_bytes), UVM_HIGH)
        repeat(num_bytes) begin
            super.body();  // 调用基础sequence
        end
    endtask
endclass

// Layer 4: 场景级sequence（组合多个协议sequence）
class uart_rx_scenario_seq extends uart_base_seq;
    rand int frame_count;
    `uvm_object_utils(uart_rx_scenario_seq)

    virtual task body();
        `uvm_info("SEQ", $sformatf("uart_rx_scenario started, %0d frames", frame_count), UVM_HIGH)
        for (int i = 0; i < frame_count; i++) begin
            `uvm_do_with(req, { data == 8'h55 + i; })  // 预填充特定数据
        end
    endtask
endclass

// Layer 5: 测试用例级sequence（组合多个场景）
class uart_normal_test_seq extends uart_base_seq;
    `uvm_object_utils(uart_normal_test_seq)

    virtual task body();
        `uvm_info("SEQ", "uart_normal_test started", UVM_HIGH)
        fork
            begin: frame_test
                `uvm_do_with(req, { num_bytes == 10; })
            end
            begin: burst_test
                `uvm_do_with(req, { num_bytes == 100; })
            end
        join
    endtask
endclass
```

在上述示例中的封装层级总结：

- Layer 1（transfer）：单个数据单元，定义数据内容和属性
- Layer 2（base_seq）：单个transfer的发送逻辑
- Layer 3（frame_seq）：多个transfer组合，形成协议帧
- Layer 4（scenario_seq）：多个帧组合，形成特定场景
- Layer 5（test_seq）：多个场景组合，形成完整测试用例

### 6.3 checker

checker一般分为静态检查和**动态检查**。验证工作中最常用的是动态检查：通过仿真器模拟实际运行，验证设计行为是否符合预期。

动态检查的主要手段包括：

- **参考模型（Reference Model）**：模拟设计功能行为
- **计分板（Scoreboard）**：对比设计输出与参考模型输出，判断是否一致
- **并行断言（Concurrent Assertion）**：对**接口信号**或**内部关键信号**之间的关系进行实时监控

除此之外，仿真结束前的**终态检查**也是验证闭环的重要环节，需要确认以下几点：

- **验证环境状态**：scoreboard中所有事务是否已匹配完成、仿真log是否存在未处理的错误或警告
- **设计状态**：状态机是否回到初始/默认状态、FIFO/Buffer等存储单元是否已清空、是否有pending未完成的事务
- **接口状态**：所有接口信号是否处于idle状态、中断标志是否已清除
- **寄存器状态**：关键寄存器的最终值是否符合预期

终态检查可通过在base_test中构建专门的end_of_test_phase或在sequence中添加 final check 来实现。

### 6.4 覆盖率组件

覆盖率是验证闭环的重要指标，用于量化验证的完备性。覆盖率组件一般包含以下类型：

- **代码覆盖率（Code Coverage）**：衡量RTL代码的执行情况，包括行覆盖率、条件覆盖率、分支覆盖率、翻转覆盖率等
- **功能覆盖率（Functional Coverage）**：衡量功能点是否被验证到，通常通过用户自定义的covergroup实现
- **断言覆盖率（Assertion Coverage）**：衡量属性（property）和序列（sequence）的触发情况

覆盖率的组织方式建议：

- 覆盖组（covergroup）应集中管理，避免散落在各个sequence中，便于统一review和维护
- 建议在env或独立的coverage collector组件中统一实例化和采样
- 覆盖组定义应与Testplan中的测试点一一对应，确保可追溯性

覆盖率豁免需谨慎，避免为追求指标而降低验证质量。

### 6.5 测试用例

测试用例的构造方式因团队而异，常见方式包括基于vseq重载或基于base_test重载等，建议与团队保持一致。

测试用例的核心职责：

- 产生激励，驱动验证环境
- 处理不便于在动态检查器中实现的场景
- 直接检查状态寄存器的值（相比动态检查更简单直观）

### 6.6 经验总结

- **agent是前期最花时间的部分**，其完备性和正确性至关重要。agent的设计需要与设计团队充分评审，确保对前后级模块的接口理解准确无误
- **checker需要迭代完善**：初期只需具备基础检查能力即可开始测试用例的开发与调试，后续逐步迭代增强
- **谨慎引入内部信号**：模块级验证中，有时不可避免需要引入内部信号来验证细节功能。引入时需与设计团队确认，并确保有相应的检查机制

## 7. 附录

### 附录A：Spec阅读检查清单

- 是否覆盖主流程、异常流程、复位流程。
- 是否明确接口时序与边界行为。
- 是否给出关键配置组合及限制条件。
- 是否识别高风险路径和外部依赖。

### 附录B：Testplan模板

建议在同级Template目录维护可复用模板文件，包含以下字段：

- 项目信息、版本与评审记录。
- 范围定义、策略选择、风险分级。
- 需求追溯表、用例分层与回归策略。
- 覆盖率目标、豁免规则与退出条件。
