## 报告体系机制

> 备注：本文基于 UVM 1800.2-2020.3.1 的 `src/base/uvm_report_object.svh`、`uvm_report_handler.svh`、`uvm_report_server.svh`、`uvm_report_catcher.svh` 源码整理。

---

## 1. 本质：报告体系解决什么问题

UVM 报告体系要解决三件事：

1. 统一消息入口（info/warning/error/fatal）
2. 可配置过滤与动作（verbosity、action、file、severity override）
3. 集中统计与后处理（计数、summary、catcher 改写）

一句话：

- `uvm_report_object` 负责“发消息”，`uvm_report_handler` 负责“算策略”，`uvm_report_server` 负责“执行与汇总”，`uvm_report_catcher` 负责“拦截改写”。

---

## 2. 关键类与数据结构

### 2.1 `uvm_report_object`

- 每个对象可持有自己的 `m_rh`（report handler）
- `uvm_report()` 先做 `uvm_report_enabled()` 检查（尤其 INFO）
- 封装成 `uvm_report_message` 后交给 `uvm_process_report_message()`

### 2.2 `uvm_report_handler`

内部有几组核心表：

1. verbosity 规则：`id_verbosities`、`severity_id_verbosities`
2. action 规则：`severity_actions`、`id_actions`、`severity_id_actions`
3. 覆盖规则：`sev_overrides`、`sev_id_overrides`
4. 输出目标：`default_file_handle`、`severity/id` 对应 file handle

### 2.3 `uvm_report_server`

- 抽象接口：`process_report_message`、`compose_report_message`、`execute_report_message`
- 全局单例入口：`set_server()` / `get_server()`（经 core service）
- 默认实现：`uvm_default_report_server`，负责计数、格式化、执行动作、最终 summary

### 2.4 `uvm_report_catcher`

- 继承 `uvm_callback`
- 用 `\`uvm_register_cb(uvm_report_object, uvm_report_catcher)` 注册
- 可读取并修改当前消息：severity/id/message/action/context/元素
- `THROW` 继续流转，`CAUGHT` 截断消息

---

## 3. 关键调用链（按时间顺序）

### 3.1 常规链路

1. 用户调用 `uvm_info/uvm_warning/...`（最终落到 `uvm_report_object::uvm_report`）
2. 构造 `uvm_report_message`
3. 进入 report 处理流程，report_catcher 先拦截
4. handler 计算有效 verbosity/action/file/severity override
5. server 进行 compose + execute
6. server 更新 severity/id 计数
7. 仿真末尾 `report_summarize()` 输出统计

### 3.2 catcher 介入点

- catcher 在 server 执行前运行，所以可以：
    - 降级/升级 severity
    - 修改 id/message/context
    - 增减 action（如加 `UVM_RM_RECORD`）
    - 直接 `CAUGHT`（不再输出）

这也是“为什么日志看起来与原始 uvm_info 调用不一致”的根因之一。

---

## 4. 常见误区与排障手段

1. 误区：`UVM_WARNING/UVM_ERROR/UVM_FATAL` 也受 verbosity 门控

默认不按 verbosity 过滤；但若被 catcher 降级为 INFO，就会受 verbosity 影响。

1. 误区：只改一个 id action 就能覆盖全部

handler 里有 severity、id、severity+id 多层规则，需看最终生效组合。

1. 误区：替换 report_server 会丢统计

`uvm_report_server::set_server()` 会先 copy 旧 server 计数，再切换。

1. 排障建议

- 打印 handler 配置（`do_print` 能看到各表）
- 检查 catcher 是否改写了 severity/id/action
- 关注 `UVM_EXIT`/`max_quit_count` 导致的提前退出

---

## 5. 复习速记

1. report_object 负责入口，handler 负责策略，server 负责执行与统计，catcher 负责拦截改写
2. 最终动作是“多层规则叠加后”的结果，不是单点配置决定
3. catcher 是最强扩展点，也最容易引入隐式行为
4. 出现“日志不符合预期”时，优先检查 catcher 与 handler 配置
5. 自定义 server 适合做统一格式、上报平台、统计扩展
